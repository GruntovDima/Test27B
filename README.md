# Test27B: четыре осмысленных входа, BS4 × 8192 токена

Набор для проверки ответов одной и той же модели на `vllm-ascend main` и на ветке
с изменениями GDN. Модель уже должна быть запущена; клиент не загружает веса,
не меняет настройки сервера и не устанавливает зависимости.

Четыре входа содержат связные отрывки из разных книг: **Alice's Adventures in
Wonderland**, **The Wonderful Wizard of Oz**, **Treasure Island** и **The Adventures
of Sherlock Holmes**. Здесь нет случайных токенов или размножения одного шаблона.
Каждый вход содержит три разных отрывка, вопросы по каждому из них и собственные
идентификаторы. В каждом документе проверяются 6 фактов и 4 идентификатора.

## Что находится в репозитории

- `inputs_source/*.txt`: четыре исходных документа с вопросами. Это ещё не входы
  ровно по 8К: их длина зависит от токенизатора.
- `fixtures/qwen3.6-27b-8k/input_*.txt`: **четыре готовых входа по 8192 токена**
  для официального Qwen3.6-27B. `pack.json` и `prompt_bs4.json` содержат точные IDs.
  `tokenizer_provenance.json` фиксирует ревизию токенизатора, ссылки и SHA256;
  `validation.json` содержит результаты проверки готовых входов токенизатором.
- `expected/*.json`: проверенные ответы по исходникам, **не сгенерированные main**.
- `cases.json`: те же документы, вопросы, допустимые варианты ответов и цитаты,
  подтверждающие ответы. Эти данные не передаются модели вместе с эталонами.
- `bs4_check.py`: подготовка точных входов, запуск BS4, оценка и сравнение с main.
- `sources/`: полные исходные тексты, лицензии внутри файлов и provenance.
- `test_checker.py`: тесты клиента и метрик; никакой модели они не запускают.

## 1. Использовать готовые входы для Qwen3.6-27B

Готовый набор уже проверен настоящим токенизатором
[Qwen/Qwen3.6-27B](https://huggingface.co/Qwen/Qwen3.6-27B/tree/6a9e13bd6fc8f0983b9b99948120bc37f49c13e9).
Каждый из четырёх входов содержит **8192 токена**, включая системное сообщение,
шаблон чата и префикс ответа с `enable_thinking=False`. Хеш набора:
`e215953a779c354da392af42751f56145759d3b456fd7a2c3ffa81a8f6961eb8`.

Для `run`, `score`, `compare` и проверки файлов токенизатора достаточно **Python 3.10+**,
никаких pip-зависимостей. Выполнять команды из корня этого репозитория.
Сверить токенизатор сервера с готовым набором:

```bash
python bs4_check.py verify-tokenizer --tokenizer /path/to/model
```

Команда проверяет SHA256 `tokenizer.json`, `tokenizer_config.json` и внешнего шаблона
чата, если он есть. При несовпадении не использовать готовые IDs вслепую: подготовить
свой набор с фактическим токенизатором сервера. Без изменений токенизатора
**дополнительная подготовка не нужна**.

Файлы `.txt` — декодированное представление для просмотра; для точного запуска
используются сохранённые IDs. Для main и PR нужен **один и тот же pack**.

Если нужен другой токенизатор/ревизия, выполнить в окружении с `transformers` и `jinja2`:

```bash
python bs4_check.py prepare --tokenizer /path/to/model --out prepared
```

При отдельной установке зависимостей подготовки использовать `requirements-prepare.txt`.

Скрипт берёт примерно равные по длине части трёх отрывков, применяет оригинальный
шаблон чата с `enable_thinking=False` и подрезает только конец третьего отрывка до
точной длины. Он проверяет, что цитаты с ответами сохранились. Ничего не дополняет
случайными словами; при недостатке текста или потере факта останавливается.
Последняя фраза отрывка может быть незавершённой — это обозначено границей отрывка.

Получатся `prepared/input_*.txt`, `prepared/prompt_bs4.json` и `prepared/pack.json`.
Для своего набора заменить `--pack` в командах ниже на `prepared/pack.json`.

Нужен `max-model-len` не меньше **8192 + 384 = 8576**; можно 9216 или выше.
`max-num-seqs` должен допускать 4 активные последовательности. Custom chat template
требует такого же шаблона в подготовке входов; текущий клиент использует шаблон из
локального токенизатора. Не подменять его шаблоном от другой модели.

## 2. Сохранить настоящий эталон на main

Запустить модель на проверяемой версии **main**. В `--revision` указать SHA именно
`vllm-ascend`, а не этого репозитория с тестами. Этот SHA записывается со слов
пользователя; клиент не может удостоверить, какие исходники загружены сервером.

```bash
python bs4_check.py run --tag main --revision MAIN_ASCEND_SHA \
  --model SERVED_MODEL_NAME --base-url http://127.0.0.1:8000 \
  --pack fixtures/qwen3.6-27b-8k/pack.json --rounds 3 --out runs/main.json
```

Температура 0, seed 42, нормальная остановка по EOS, максимум 384 выходных токена.
JSON запрашивается обычным текстом; принудительное constrained decoding не
используется. Одна HTTP-заявка содержит четыре разных tokenized prompts, `n=1`.
Клиент требует четыре ответа и `usage.prompt_tokens == 32768`.

Три повтора помогают увидеть нестабильность самого main. Его ответы могут быть
ошибочными: эталон main не заменяет проверенные ответы в `expected/`.
Записать версии весов, dtype/quantization, CANN, vLLM, torch-npu, серверную команду,
устройства, TP и состояние кеширования. Можно передать это через
`--metadata metadata.json`, заполнив `metadata.example.json`.

## 3. Выполнить тот же тест на ветке с GDN

Использовать те же веса, токенизатор, параметры запуска и **тот же pack**:

```bash
python bs4_check.py run --tag pr --revision PR_ASCEND_SHA \
  --model SERVED_MODEL_NAME --base-url http://127.0.0.1:8000 \
  --pack fixtures/qwen3.6-27b-8k/pack.json --rounds 3 --out runs/pr.json

python bs4_check.py compare --main runs/main.json --candidate runs/pr.json \
  --out runs/comparison.json
```

Смена хеша входов, размера батча, числа входных токенов или sampling-параметров
блокирует сравнение. Клиент не удостоверяет идентичность весов/бинарников — это
надо проверить по настройкам и журналу сервера. Существующие run-файлы не перезаписывает.

## Как считается точность

Основная метрика — **factual accuracy**: число верных ответов по содержанию / число
вопросов по содержанию. Один BS4 содержит 24 таких вопроса. Например, 23/24 = 95.83%.
При трёх повторах знаменатель 72; это повторения 24 вопросов, а не 72 независимых
примера. Отдельно считаются 16 идентификаторов за один BS4, чтобы увидеть смешивание
последовательностей. Их нельзя использовать для завышения factual accuracy.

Также считаются:

- все поля вместе: 40 проверок за один BS4;
- fully correct documents: сколько из 4 документов имеют все верные поля,
  строго правильный набор ключей и завершённый ответ;
- valid JSON и valid schema;
- semantic agreement with main: совпадение полей с наблюдавшимися ответами main;
- lost stable-correct main fields: поля, правильные во всех повторах main,
  но ошибочные хотя бы в одном повторе PR;
- изменение точности в **процентных пунктах**.

Порядок ключей, регистр, пробелы и пунктуация не влияют на сравнение значений;
допустимы только явно перечисленные синонимы. Например, `Caucus-race` и `caucus race`
равнозначны. Произвольный длинный ответ с правильным словом внутри не засчитывается.
Неверный факт, отсутствующее поле или незавершённый ответ — ошибка. Дубли JSON-ключей,
дополнительные реплики и зацикливание не принимаются как валидный JSON.

Совпадение с main не означает правильность: main тоже может отвечать неверно.
Различие свободного текста само по себе не доказывает ошибку ядра: vLLM не
гарантирует воспроизводимость по умолчанию
([документация](https://docs.vllm.ai/en/v0.20.1/usage/reproducibility/)).
Этот тест не меняет режим batch invariance и другие вычислительные настройки.

Коды завершения: `run`/`score` — 0 только при всех правильных документах, иначе 1;
`compare` — 1 при падении точности/потере устойчиво верных полей main, 2 при
нестабильном или невалидном main без обнаруженного падения, 0 при отсутствии
обнаруженной регрессии на этом наборе. Неверный запрос/повреждённый pack/HTTP-ошибка
останавливают скрипт, не дают PASS. Проверять отчёт, а не только код процесса.

## Уже есть ответы из своего скрипта

Сохранить JSON в формате `{"generated_texts": ["ответ 1", "ответ 2", "ответ 3", "ответ 4"]}`
в порядке Alice, Oz, Treasure Island, Holmes. Допускается и просто массив четырёх строк.

```bash
python bs4_check.py score --outputs my_outputs.json --out runs/my_score.json
```

При импорте только текстов завершение по EOS проверить нельзя: в отчёте будет
`finish_reason_unverified`. Можно оценить содержание, но не утверждать нормальное
завершение генерации. Для сравнения с main лучше использовать сохранённые `run`-файлы.

## Ограничения

Четыре документа — небольшой factual smoke test. Произведения могли встречаться
в обучении модели; коды отрывков требуют чтения текущего контекста, но это не
доказательство обработки всех 8К. Успех не сертифицирует GDN, все модели или общую
точность. Для локализации вычислительной ошибки нужны отдельные проверки ядра/logits.

BS4 здесь означает четыре входа в одной заявке. Планировщик, chunked prefill и лимиты
могут разбить их на другие фактические батчи. Для проверки именно BS4 ядра надо
смотреть серверный trace. Повторные запросы могут попадать в prefix cache:
8192 логических входных токена не гарантируют 8192 заново вычисленных токена
prefill. Для холодного prefill контролировать кеш в собственном тестовом сервере
одинаково на main и PR. Клиент не сбрасывает чужие кеши и не перезапускает сервер.

## Проверка клиента

```bash
python -m unittest discover -p test_checker.py -v
```

В локальной разработке прошли 15 тестов: проверка эталонов по цитатам, хеши исходников, partial credit,
aliases, перестановка последовательностей, невалидные/зацикленные/обрезанные ответы,
клиппинг ровно 8192, сохранение свидетельств, сравнение main и отказ при несовместимых
входах, сортировка ответов API и контроль 32768 входных токенов, целостность готовых
файлов, отказ при чужом токенизаторе и обработка формата нового Transformers.
API и часть токенизаторных тестов подставные. Отдельно настоящий официальный
токенизатор подготовил четыре входа по 8192; проверены сохранившиеся цитаты,
шаблон ответа и хеши. **Модель и сервер main здесь не запускались**; ответов main
в репозитории нет, их надо записать командой `run` рядом с доступным сервером.
