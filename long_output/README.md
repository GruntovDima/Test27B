# HQ_TEST: TP4, четыре запроса, 8K вход / ~8K содержательный выход

Это **другой тест**, чем книжный `bs4_check.py` в корне репозитория. Здесь каждый
ответ действительно должен содержать около8192 токенов: преобразование длинного
реестра покупок в JSON Lines. Четыре разных входа, независимый Python-эталон,
5856 проверяемых полей. Не GSM8K и не оценка общего интеллекта модели.

## Запуск одной командой

В контейнере уже должны быть установленная **HQ_TEST**, совместимый vLLM0.24,
CANN/torch-npu и модель Qwen3.6-27B W8A8. Скрипт ничего не устанавливает,
не меняет ядра/веса и не останавливает чужие серверы. Для запуска/оценки нужен
только Python3.10+; подготовка нового набора дополнительно требует transformers.

```bash
git clone https://github.com/GruntovDima/Test27B.git
cd Test27B
source /usr/local/Ascend/ascend-toolkit/set_env.sh

ASCEND_RT_VISIBLE_DEVICES=0,1,2,3 python long_output/run_test.py \
  --model-path /home/models/Qwen3.6-27B-w8a8
```

Если репозиторий уже скачан: `git pull --ff-only`. Путь к модели замените своим.
Используйте четыре **свободные** карты: `npu-smi info`. Номера зависят от проброса
устройств в контейнер; `0,1,2,3` не обязательно физические номера на хосте.
Отсутствие свободных устройств не разрешает останавливать чужие процессы/reset.
Никакие optimization exports для автоматической HQ_TEST не требуются.

Скрипт поднимет сервер на порту8000, дождётся `/health`, отправит четыре streaming
запроса, напечатает оценку и задержки, затем завершит **только свой** сервер.
Если порт занят, завершится с ошибкой, а не подключится к чужому серверу.
Результаты: `long_output/runs/ДАТА-PID/`, путь печатается перед стартом.

Для другого порта или повторов:

```bash
ASCEND_RT_VISIBLE_DEVICES=0,1,2,3 python long_output/run_test.py \
  --model-path /home/models/Qwen3.6-27B-w8a8 --port 8001 --rounds 3
```

Добавьте `--revision ТОЧНЫЙ_SHA_HQ_TEST`, чтобы записать ревизию в metadata.
Это указанная пользователем ревизия, не доказательство реально загруженного
binary. Автоматически записываются версии пакетов, CANN, хеши конфигов и
токенизатора, список/размеры/mtime весов и команда сервера. Полные весовые
SHA256 не вычисляются; для строгого A/B отдельно проверяйте источники/бинарники.

Launcher ориентирован на проверенный vLLM0.24/HQ_TEST, не на arbitrary main.
TP4, max-num-seqs4, maxlen20480, prefill-budget1280, chunked prefill,
FULL_DECODE_ONLY capture[4], prefix cache off, FP16 activations/state,
checkpoint quantization unchanged. Без DFlash/pruning/profiler. Никакого
автоматического перехода на eager при ошибке. Скрипт выполняет проверку качества
без прогрева; для стабильного сравнения скорости нужен отдельный warmup/protocol.

## Метрики и результат

В консоли и `run.json` находятся:

- Правильные факты/5856, правильные строки, JSON/schema, завершённость и длины.
- `mean_ttft_ms`: среднее время от отправки до первого **непустого текстового**
  SSE-события (whitespace считается текстом).
- `mean_tpot_ms`: среднее `(последний текст − первый текст)/(output_tokens−1)`.
- `token_weighted_tpot_ms`: сумма интервалов генерации / сумма `(output_tokens−1)`.
- Восемь сегментов по позициям **эталонных** строк, чтобы проверять конец ответа.

Число output_tokens берётся из server usage, **не из числа HTTP/SSE-чанков**.
Usage trailer не продлевает TPOT. Время отдельного EOS/пустого события из этого
текста не восстановить: это client-observed приближение, не kernel timing и
не обещание совпадения с AIS-Bench. Один токен/нет timing evidence: TPOT=N/A.
Средние включают только завершённые ответы с валидным usage; счётчики сохраняются.
Клиентская concurrency4 не гарантирует BS4 каждого kernel: prefill/tail различаются.

`max_tokens=12288`, EOS **не отключён**, вход каждого запроса ровно8192 IDs
с chat template/thinkingoff. Входы уже подготовлены настоящим токенизатором;
launcher сверяет его файлы. Если хеш отличается, не подавайте чужие IDs:

```bash
python long_output/long_quality.py prepare \
  --tokenizer /path/to/model --background long_output/sources/pg11.txt --out my-fixtures
```

Этот альтернативный pack запускайте клиентом `long_quality.py run --pack
my-fixtures/pack.json ...` на уже готовом сервере с заполненным metadata.
Однокомандный launcher намеренно использует замороженный проверенный pack.

PASS требует **всех** правильных полей/строк, естественного stop/DONE, usage,
структуры и фактического выхода>=8192 у каждого запроса. Отсутствующие/дублированные
записи, неверные факты, лишние поля, обрыв/лимит не проходят. Фактическая точность
показывается и при FAIL. Корректный ответ<8192 не считается полным8K workload.
Не дописываем фиктивные токены после EOS. Run exit1 при qualityFAIL — это не
обязательно падение сервера; смотрите JSON и server.log.

## Пересчитать сохранённый результат

Без повторного запуска модели:

```bash
python long_output/long_quality.py score \
  --run long_output/runs/ДАТА-PID/run.json --out score-with-timing.json
```

`run.json` сохраняет запросы, SSE, ответы, usage, provenance и score.
`progress/*.json` — частичные checkpoints, не финальная оценка.
При трёх повторах файл checkpoint отражает последний повтор; полные ответы
завершённых волн находятся в `run.json`. Это повторы тех же примеров, не12новых задач.

Тесты клиента (без NPU):

```bash
python -m unittest discover -s long_output -p 'test_*.py'
```
